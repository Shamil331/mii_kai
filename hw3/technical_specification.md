# Техническое задание — NutriDay (MVP)

## 1. Описание проекта

**NutriDay** — адаптивное веб-приложение для заказа готовых наборов здорового питания на день или неделю с оплатой и доставкой.

Цель MVP: пользователь проходит путь «выбор рациона/меню → корзина → дата и адрес → оплата → подтверждение» без сложной кастомизации блюд, без собственной курьерской логистики и без AI-рекомендаций.

Срок разработки MVP (учебный ориентир): до 3 месяцев.

## 2. Целевая аудитория

- Возраст: 25–45 лет  
- Ограниченный бюджет, мало времени на готовку  
- Устройства: смартфон и десктоп (mobile-first responsive)  
- Ожидание: готовые наборы, прозрачная цена, быстрый чекаут  

Персоны: Анна (скорость выбора), Игорь (контроль суммы), Марина (дата и адрес доставки) — см. `user_stories.md`.

## 3. Функциональные требования

Требования сформулированы в измеримом стиле: «Система должна…». Источник: пользовательские истории US-01…US-07.

### 3.1. Каталог и меню наборов (US-01)

1. Система должна отображать список доступных типов питания и карточки наборов при успешной загрузке раздела «Наборы», чтобы пользователь мог сравнить варианты без регистрации (если гостевой доступ предусмотрен в MVP).  
2. Система должна показывать у каждой карточки набора название, длительность (день или неделя) и цену в валюте интерфейса, чтобы пользователь мог оценить стоимость до добавления в корзину.  
3. Система должна открывать детальный просмотр состава набора по действию пользователя (клик/тап по карточке или «Подробнее»), чтобы пользователь увидел перечень позиций меню.  
4. Система должна не предоставлять UI глубокой кастомизации отдельных блюд в MVP, чтобы сохранить фиксированные наборы.

### 3.2. Корзина (US-02, US-03, US-07)

5. Система должна добавлять выбранный набор в корзину с количеством ≥ 1 при нажатии «Добавить в корзину», чтобы позиция появилась в заказе.  
6. Система должна увеличивать количество существующей позиции на 1 при повторном добавлении того же набора, чтобы не дублировать строки без необходимости.  
7. Система должна отображать в корзине для каждой позиции название, цену за единицу, количество, сумму по позиции и общий итог, чтобы пользователь контролировал бюджет.  
8. Система должна изменять количество позиции по кнопкам «+» и «−» и мгновенно пересчитывать суммы позиции и заказа, чтобы итог всегда соответствовал составу корзины.  
9. Система должна удалять позицию из корзины при уменьшении количества с 1 до 0, чтобы в заказе не оставались нулевые строки.  
10. Система должна показывать пустое состояние корзины с CTA «К наборам» и блокировать оформление, когда позиций нет, чтобы пользователь мог вернуться к каталогу.

### 3.3. Оформление: дата и адрес (US-04)

11. Система должна запрещать выбор даты доставки раньше даты «текущая календарная дата + 2 дня» при оформлении заказа, чтобы соблюсти минимальный срок производства.  
12. Система должна сохранять выбранную доступную дату доставки в черновике заказа после подтверждения шага даты, чтобы дата участвовала в оплачиваемом заказе.  
13. Система должна требовать непустой валидный адрес доставки перед переходом к оплате и показывать сообщение об ошибке при нарушении, чтобы курьер/служба доставки получила корректные данные.

### 3.4. Оплата и подтверждение (US-05)

14. Система должна создавать заказ со статусом оплачен/подтверждён только после успешного ответа платёжного провайдера, чтобы неоплаченные попытки не считались завершёнными.  
15. Система должна отображать экран подтверждения с идентификатором заказа, датой доставки, адресом и суммой после успешной оплаты, чтобы пользователь получил доказательство оформления.  
16. Система должна очищать корзину от оплаченных позиций после успешной оплаты, чтобы повторная оплата тех же позиций не происходила случайно.  
17. Система должна сохранять состав корзины и черновик заказа и показывать сообщение с возможностью повтора при отклонённой или отменённой оплате, чтобы пользователь мог завершить покупку без потери данных.

### 3.5. Онбординг (US-06)

18. Система должна при первом визите (или при отсутствии флага прохождения) показывать краткий блок ценности: выбор рациона → набор → оплата и доставка с правилом «+2 дня», с CTA в каталог и возможностью пропустить, чтобы снизить неопределённость нового пользователя.

### 3.6. Зависимости (для реализации)

| Требование / история | Зависит от |
|----------------------|------------|
| US-02 Добавление в корзину | US-01 (существование набора в каталоге) |
| US-03 Изменение количества | US-02 (непустая или ранее наполненная корзина) |
| US-04 Дата и адрес | US-03 / непустая корзина |
| US-05 Оплата | US-04 (дата + адрес) |
| US-07 Пустая корзина | независима; дополняет US-03 |

**Оптимизация (один вариант):** объединить отображение итога корзины в единый компонент пересчёта (требования 7–9), чтобы исключить расхождение сумм на экране корзины и на чекауте. Логика историй и зависимостей не нарушается: меняется только способ реализации единого источника истины для `total`.

## 4. Нефункциональные требования

1. Система должна отдавать первый осмысленный контент каталога (или скелетон с последующим контентом) не позднее **3 секунд** при нормальном сетевом условии эмуляции 4G в тестовой среде.  
2. Система должна корректно отображать основные сценарии (каталог, корзина, чекаут) на ширине viewport **от 360 px** и **от 1280 px** без горизонтальной прокрутки контента страницы.  
3. Система должна пересчитывать итог корзины на клиенте **не дольше 200 мс** после изменения количества (локальная операция без сети).  
4. Система должна отображать интерактивные элементы оформления (кнопки добавления, степперы, CTA оплаты) с минимальной областью нажатия **44×44 CSS px** на мобильной ширине.  
5. Система должна использовать HTTPS для всех страниц оформления и оплаты в рабочей среде.  
6. Система должна сохранять содержимое корзины между перезагрузками страницы в рамках одной сессии браузера (например, `localStorage` или эквивалент) не менее чем до успешной оплаты или явной очистки.  
7. Система должна показывать тексты ошибок и пустых состояний на русском языке в UI MVP.

## 5. Обработка ошибок и UX-решения

### 5.1. Валидация ввода

| Ситуация | Поведение системы | UX |
|----------|-------------------|-----|
| Пустой адрес | Блокировка перехода к оплате | Инлайн-ошибка у поля: «Укажите адрес доставки» |
| Некорректный формат адреса (слишком короткий / только пробелы) | Отклонение submit | Подсветка поля + короткий текст правила |
| Дата &lt; сегодня+2 | Дата недоступна в пикере | Disabled-дни в календаре + подсказка «Доставка не ранее чем через 2 дня» |
| Попытка оформить пустую корзину | CTA неактивен или редирект | Пустое состояние + «К наборам» |

### 5.2. Пустые данные

| Ситуация | UX |
|----------|-----|
| Каталог без наборов | Экран «Наборы временно недоступны» + предложение обновить |
| Пустая корзина | Иллюстрация/текст + CTA в каталог; итог и оплата скрыты/disabled |
| Нет типов питания | Сообщение об отсутствии фильтров; каталог без чипов или с одним «Все» |

### 5.3. Сеть

| Ситуация | UX |
|----------|-----|
| Таймаут / offline при загрузке меню | Баннер «Нет соединения» + кнопка «Повторить» |
| Ошибка при создании заказа / оплате | Сохранение черновика; сообщение «Не удалось завершить оплату»; «Повторить» |
| Медленная загрузка | Скелетоны карточек, без «пустого мигания» контента |

### 5.4. Неавторизованный доступ

| Ситуация | UX |
|----------|-----|
| Действие требует сессии (если оплата/заказ привязаны к аккаунту) | Модалка/страница входа с возвратом на чекаут после успеха |
| Истёкшая сессия на шаге оплаты | Сообщение «Войдите снова», корзина не очищается |
| Прямой URL чекаута без корзины | Редирект в корзину или каталог с пояснением |

*Если в MVP допускается гостевой чекаут: система должна собирать контакты (email/телефон) как обязательные поля вместо полноценной авторизации — с той же валидацией пустых значений.*

## 6. Негативные сценарии (≥3 типов) и UX

### Тип A — Отказ / сбой оплаты
- **Сценарий:** банк отклонил карту; пользователь закрыл виджет оплаты.  
- **Ожидание:** заказ не в статусе «оплачен»; корзина и дата/адрес сохранены.  
- **UX:** понятная ошибка, кнопки «Повторить оплату» и «Изменить данные заказа»; без ложного «успеха».

### Тип B — Недоступная дата / нарушение lead time
- **Сценарий:** пользователь пытается выбрать завтра при правиле +2 дня; или дата стала невалидной из-за смены полуночи.  
- **Ожидание:** система не принимает недоступную дату.  
- **UX:** disabled-даты; при устаревании выбора — предупреждение и принудительный повторный выбор.

### Тип C — Пустой / конфликтующий состав заказа
- **Сценарий:** набор сняли с продажи между добавлением и оплатой; или корзина очищена на другой вкладке.  
- **Ожидание:** оплата не проходит с устаревшими позициями.  
- **UX:** сообщение «Некоторые наборы недоступны», список проблемных позиций, предложение удалить их или обновить каталог.

### Дополнительно (рекомендуется в тестах)
- Двойной клик по «Оплатить» не создаёт два оплаченных заказа (идемпотентность / disabled кнопки на время запроса).

## 7. Критерии приёмки MVP (сводка)

- [ ] Каталог типов питания и наборов отображается с ценой и длительностью  
- [ ] Корзина: add / ± / удаление при 0 / корректный итог  
- [ ] Дата доставки ≥ сегодня + 2 дня; адрес обязателен  
- [ ] Успешная оплата → подтверждение с ID; неуспех → без ложного подтверждения  
- [ ] Обработаны валидация, пустые состояния, сеть, unauthorized/guest edge cases  
- [ ] Responsive 360 / 1280
